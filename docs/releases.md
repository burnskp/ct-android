# Release signing and publication

Public APKs use a dedicated signing key. Keep it for every future update and maintain a secure backup outside this repository. Never use a debug key for public releases. No production key is generated by the build.

## One-time key setup

With JDK 17, create a keystore outside the checkout (this command prompts for a password and certificate identity):

```sh
mkdir -p "$HOME/.android-release"
keytool -genkeypair -keystore "$HOME/.android-release/couch-tasks.jks" \
  -storetype JKS -alias couch-tasks-release -keyalg RSA -keysize 3072 -validity 10000
```

Use a strong password and retain both store and key passwords. Certificate identity is public in the APK. Back up the keystore and passwords securely; losing them can prevent updates to installed APKs.

## Local public release

Enter the Nix shell, or provide JDK 17, Python 3, Git, GNU Make, Bash, and `ANDROID_HOME` with Build Tools 37.0.0. Commit the release changes and create or check out the release tag first (for example, `git tag v0.1.0`). `make release` requires exactly one `v*` tag on `HEAD` and validates it before building or signing. Supply these environment variables using a password manager or interactive prompts, not command-line password arguments:

```sh
export ANDROID_KEYSTORE_PATH="$HOME/.android-release/couch-tasks.jks"
export ANDROID_KEY_ALIAS=couch-tasks-release
read -rs -p 'Keystore password: ' ANDROID_KEYSTORE_PASSWORD; echo
read -rs -p 'Key password: ' ANDROID_KEY_PASSWORD; echo
export ANDROID_KEYSTORE_PASSWORD ANDROID_KEY_PASSWORD
make release
unset ANDROID_KEYSTORE_PASSWORD ANDROID_KEY_PASSWORD
```

The verified APK is `app/build/outputs/apk/release/app-release.apk`. Missing credentials fail; signing never falls back to the debug key. For local debug-key builds use `make sideload` instead.

## GitHub tag releases

Before the first release, create a protected **release** environment under Settings → Environments and put the following secrets **only in that environment**, not in repository or organization secrets. The `publish` job references this environment; the unsigned build and pull-request jobs do not.

Require approval from designated release maintainers, prevent self-review, and disallow administrator bypass where the repository plan supports it. Restrict environment deployments to protected release tags matching `v*`. Add a tag ruleset that restricts creation, update, and deletion of these tags to the release maintainers; protect `main` with reviewed pull requests and passing checks. Only release maintainers may approve publication. Review the tagged commit and its workflow changes before approval, and verify that it belongs to protected `main`. An environment name in YAML alone does not enable these protections. Do not publish until all protections are configured.

Both workflows pin third-party actions to full commit SHAs resolved from their upstream version tags. Dependabot remains enabled for SHA updates; review those updates before merging.

Environment secrets:

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | Base64 encoding of the dedicated keystore file |
| `ANDROID_KEYSTORE_PASSWORD` | Keystore password |
| `ANDROID_KEY_ALIAS` | `couch-tasks-release`, or your chosen release alias |
| `ANDROID_KEY_PASSWORD` | Key password |

Base64 is encoding, not encryption. Transfer its output directly to the secret store; do not commit it or print it in CI logs. Keep secrets out of issues and pull requests.

For each release:

1. Run `make verify` with an emulator/device and commit any release changes.
2. Push the commit to main, then create and push the next release tag, for example `git tag v0.1.0` and `git push origin v0.1.0`. No version file edits are needed.

Both CI and `make release` derive `versionName` from the tag without the `v` prefix and calculate `versionCode` as `major * 1000000 + minor * 1000 + patch`. For example, `v1.2.3` produces `1.2.3` / `1002003`. Tags must be `vMAJOR.MINOR.PATCH` with no leading zeros or prerelease/build suffixes. Minor and patch must be at most 999, and the resulting code must be between 1 and 2100000000. Publish increasing versions; confirm the next code exceeds that of any previously distributed APK. The former `0.1.0` / `1` becomes `0.1.0` / `1000` under this scheme.

The workflow passes the derived values through the Gradle properties `releaseVersionName` and `releaseVersionCode`; both must be supplied together. Ordinary builds without these properties (including PR builds and `make sideload`) use `0.0.0-dev` / `1` and require no Git tags. Rebuilding a release tag produces the same version values.

The tag workflow rejects malformed or out-of-range tags, runs version-script tests, unit tests and debug/release lint, builds an unsigned minified release, and signs it in a separate job. Only the publishing job has repository write permission. Signing credentials are never supplied to pull-request jobs. Temporary keystore material is removed even if signing fails.

The GitHub Release contains `couch-tasks-vMAJOR.MINOR.PATCH.apk` and `SHA256SUMS`. Verify downloads with `sha256sum -c SHA256SUMS`. Existing releases/assets are not overwritten; a rerun after publication fails rather than replacing binaries. Inspect Actions logs for failures and correct configuration before retrying. No Play Store upload is configured.

## Existing debug installations

A release-key APK cannot normally update an installation signed with a different debug key. Before uninstalling a debug installation, sync and verify all desired tasks on another client/server. Uninstalling removes local data, and Android backup/device transfer is disabled for that data. If sync is blocked, preserve and repair the existing installation before replacing it. Subsequent public releases must keep the same signing key and increase `versionCode`.

## Release verification gate

Run unit tests, debug and release lint, debug and release builds, and instrumentation compilation:

```sh
./gradlew --continue testDebugUnitTest lintDebug lintRelease assembleDebug assembleRelease assembleDebugAndroidTest
```

Run `./gradlew connectedDebugAndroidTest` on both API 26 and API 37 before release. This includes schema 3→4 migration, project child preservation, canonical merges, tombstones, share draft idempotency, and persistent switch recovery tests. Exercise the share confirmation screen with external intents, cancellation, edits and recreation, and test a real server switch with a lost response after server commit and process termination before activation. Confirm the old dataset remains active until successful activation and retry creates no duplicate identities. Instrumentation compilation is not a substitute for these device runs.

Run Gitleaks against the exact publishable tracked snapshot, including uncommitted additions intended for the release, with redacted output. Inspect workflow permissions and Android backup exclusions: profiles and journals live in the excluded app database, profile passwords in the excluded encrypted preferences, and staged databases under `noBackupFilesDir`. No APK may be distributed until these gates pass. Keep dependency upgrades separate from release hardening unless a relevant vulnerability or compatibility requirement is established.
